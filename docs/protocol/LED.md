# SMK 37 Pro — LED-протокол

Рабочая справка для секвенсора. LED-утилиты в `tools/` заморожены.
Пользователь подтвердил стабильность их режима «Максимум»; перенос на JUCE
проверен по байтам, но ещё ожидает проверки на устройстве.

## Сообщение

Для записи `n` (1–32): RGB начинается с `0x11B + (n−1) × 0x4A`,
следующий байт — LED enable. Используем 0 для выключения и 255 для включения.
Это не плавная яркость; для градиента меняется RGB.

- Data: регион `05`, адрес 4 байта LE, число значений 3 байта LE, значения.
- Логический пакет: `00 59 22`, длина Data 3 байта LE, Data, `(~sum(Data)) & 255`.
- Весь логический пакет упакован потоком младших битов в 7-битные байты, между F0 и F7.
- RGB+enable отправляются одним блоком из четырёх значений.
- ACK: `F0 00 32 01 08 00 00 00 00 7F 01 F7`.
- Только одна неподтверждённая запись; без добавленной паузы. Таймаут останавливает отправку без автоматического повтора.

Адреса относятся к проверенной конфигурации (индекс 0). Универсальная работа
с произвольными пресетами не заявлена; отдельную систему управления ими не разрабатывать.
Постоянный Save не используется. Банк 1 следует [физической карте](../controller.md);
привязку адресов банка 2 к физическим позициям не считать полностью проверенной.
Не обещать обновление всех пэдов за <100 мс без измерения.

## Ограничения, предотвращающие повтор багов

Рабочая Python-основа — pad-one `2770a7a` и последующая простая утилита 0.3.1.
Не возвращать отвергнутые транспорты `5b53c6e`, `d373abe`, `ec35bf8`, `0feb67f`.
В `python-rtmidi 1.5.8` нет `MidiIn.set_buffer_size`: такой вызов ломал Windows
до открытия портов, поэтому SysEx вообще не отправлялся. Не переносить методы
из C++ API в Python по предположению. Не делать чтение полного пресета условием LED-записи.
Обеспечивать приём SysEx/ACK и не открывать один MIDI-вход дважды.
